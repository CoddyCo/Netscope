# Auto-Diagnosis & Heuristics Engine

The `AutoDiagnosis` module (`netscope/core/auto_diagnosis.py`) is the analytical core of NetScope. It replaces manual network log parsing with programmatic heuristics to assign semantic context to raw network telemetry.

## System Objectives
Traditional network tools output raw matrices (Hop #, IP, Latency). The Auto-Diagnosis engine transforms this data into actionable insights by detecting:
- Control Plane vs Data Plane discrepancies.
- Geographic constraints (physics limitations).
- Hardware limits (Rate Limiting).
- Routing anomalies (BGP shifts).

## 1. The Scoring Algorithm (HealthScore)
The `HealthScore` class enforces a strict deduction model. Every trace begins at `100` (perfect health) and is subjected to penalties.

### Mathematical Penalties
- **Target Endpoint Loss**: $Penalty = Loss\% \times 0.6$. Loss is only penalized if the *final* destination fails to respond. Intermediate packet loss is ignored to prevent false positives caused by intermediate router deprioritization.
- **Jitter / Latency Spikes**: The engine calculates the standard deviation ($\sigma$) of the latency array. A penalty of `-10` is applied if $Max(Latency) > \mu + (1.5 \times \sigma)$ AND the spike exceeds a static $50ms$ threshold.
- **Complete Timeout**: A flat `-20` penalty if the endpoint is completely unreachable (100% loss).

## 2. Heuristic Bottleneck Detection
The engine evaluates the hop sequence $H = [h_1, h_2, ..., h_n]$ to identify localized failures.

### The "ICMP Rate Limiting" Trap
**The Problem**: Core internet backbone routers aggressively rate-limit ICMP TTL-exceeded generation to protect their CPU control planes. To a standard traceroute, this looks like massive packet loss (100%) or severe latency (500ms) at a specific hop.
**The NetScope Solution**: 
The engine implements a $O(n)$ look-ahead algorithm:
```python
if H[i].loss > 0 or H[i].latency > threshold:
    if H[i+1].latency < H[i].latency and H[i+1].loss == 0:
        # H[i] is artificially rate limiting ICMP. It is NOT a bottleneck.
        flag_as_rate_limited(H[i])
```
This isolates true data-plane packet loss from control-plane ICMP throttling.

### Geographic Latency Suppression
**The Problem**: A packet crossing the Atlantic Ocean (e.g., London to New York) takes approximately ~70-90ms due to the speed of light through fiber optics. A naive system will flag this as a "latency spike".
**The NetScope Solution**:
The engine correlates hop telemetry with MaxMind GeoIP datasets.
If $H[i].country\_code \neq H[i+1].country\_code$, the engine calculates the theoretical minimum latency based on the great-circle distance between the two coordinates. If the observed latency delta $\Delta$ is within $1.2x$ of the theoretical distance bound, the spike is suppressed and classified as an "International Link Crossing".

### First-Mile / ISP Edge Detection
If a significant latency delta occurs between $h_1$ (Local Gateway) and $h_2$ (ISP Edge Router), the engine flags this as `WIFI_CONGESTION` or `LAST_MILE_SATURATION`, directing the user to investigate their local router rather than their ISP.

## 3. Data Output
The resulting `Diagnosis` dataclass contains:
1. `severity`: Evaluated string enum (`INFO`, `WARNING`, `CRITICAL`).
2. `root_cause`: A semantic string generated by the engine.
3. `bottlenecks`: An array of specific `Bottleneck` structs pointing to the exact offending IP address and its percentage contribution to total trace time.
